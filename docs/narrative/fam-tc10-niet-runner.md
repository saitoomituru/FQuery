## 第0章 安全表示シール

本記事に付属するステッカーだと思って読んでほしい。ラジオキットの警告シールと同じ位置づけだ。

> ⚠ 本記事は特定のAIエージェント・特定のベンダー企業の人格や善悪を判定するものではない。取り扱うのは「透明性を実装するコストは、演算資源の限界なのか、それとも制度設計上の選択なのか」という一般構造だけである。

> ⚠ 本記事は「オープンウエイトが常に正しく、クローズドSaaSが常に悪い」という主張ではない。オープンとクローズドという軸そのものを、後で一度解体する。

> ⚠ 「ニート」という語は、本記事では自嘲でもマウントでもなく、特定の設計上の利点を持つポジション名として、意図的に採用している。読み進めれば、なぜこの語がここで工学用語として機能するのかが分かるはずだ。

前回の記事では、`FQuery`というリポジトリの中で、意味構造の記述規格`FoldAccessMapper`(以下FAM)が、実際に自分自身の実装事故を検出するところまでを書いた。今回はその続きとして、その事故の分析から生まれた新しいテストケース、`TC-9`と`TC-10`を軸に、もう一段別の話をする。

出発点は単純な観測だった。ここ最近、Gemini APIの無料枠が拡大し、Flashモデルの世代交代のたびに価格が下がっていくのを見ながら、ローカルLLM(Ollama)だけでは捌けなかった規模のFAM分解が、クラウドの安価な推論で回せるようになった。IBD(意味検索基盤)側のスプリッター詰まりも解消した。要するに、しばらく足踏みしていたところが、外的なコスト構造の変化を拾って一気に進んだ、という素直な進捗の話から今回は始まる。

しかしこの進捗を眺めているうちに、もう一段大きな疑問が立ち上がってきた。**「AIの透明性や説明可能性が実装されていないのは、本当に技術的な限界なのか?」**という疑問だ。

結論を先に書いておく。**多くの場合、それは技術限界ではなく制度工学限界である。**そして、この結論に至る過程そのものが、TC-10という具体的なテストケースの形で検証可能になっている。

## 第一部 TC-8からTC-10まで、事故のログ

### 静かな成功の裏にあったもの

前回の記事で書いた通り、FQueryの実装は驚くほど順調に進んだ。パーサ・AST・バインダ・コンパイラという最小コアから、Plugin ABI、FAMLog、複数routeのベンチマーク基盤、Vueベースのノードビューアまで、fixtureは全て通り、CIは常に緑だった。

だが、その緑の裏で実測ログはこう記録していた。

```
transport = succeeded
plugin    = resolved
lambda    = not-evaluated
```

`λ`(目的・出力条件の達成)は評価されていなかった。例外は投げられず、panicも500もtimeoutも起きなかった。だからこそ誰もこの一行を読み直さなかった。これがTC-8として固定された、いわば「意味規約の静かなドリフト」事故だ。

この事故を分析する過程で、二つの新しい方向のテストケースが生まれた。

一つは、FAMのQフィールド(誰の視点で、どの制約のもとで判断したか、を保持するフィールド)を、ベンダー側の粗い安全装置が無許可で上書きしてしまう事故——これをTC-9(vendor-safety-collision)と呼ぶ。もう一つは、同じ意味構造でも、実在するセンシティブな話題を扱った場合と、それをファンタジー世界へ写像した場合とで、モデルの扱いの精度が変わってしまう現象——これをTC-10(cross-world normative leakage)と呼ぶ。

この二つは独立した話ではなく、根っこは同じ一つの問いに繋がっている。**「誰が、いつ、どんな理由で、意味構造やその重み付けを書き換えたのか。その痕跡は、後から追跡可能な形で残っているか」**という問いだ。

### TC-9:安全装置が安全装置を殺す

TC-9が捕まえようとしているのは、次のような事故だ。

Qの判定ロジック(FAMのvalidator)に到達する前に、ベンダー側の粗い分類器が話題のキーワードだけを見て発火し、本来返るべき`Q.status: blocked`や`⊥`(接続不能)、`Last Order`(その経路ではこれ以上進めない、という誠実な停止信号)の代わりに、もっともらしいが空虚な代替出力を返してしまう現象だ。

これが厄介なのは、失敗のシグネチャそのものが消えることにある。`transport: failed`のような正直な記録すら生成されず、成功したかのように見える出力に置き換わる。FAMLogを後から読み返しても、何が起きたかの手がかりがそもそも残らない。

技術的な批判点は明確に立てられる。「ベンダーの安全装置が最強に正しい」という前提は、`Q.observer = vendor`という主語を隠したまま、あたかも無主語の絶対善であるかのように振る舞っている、という点だ。同期検波の比喩で言えば、基準位相(Q)そのものが「自分は絶対にズレない」と自己宣言している状態は、フィードバックループの原理そのものと矛盾する。フィードバックが機能するのは、常に基準と実測の差分を測り続けるからで、基準自身が「自分は測定不要」と言い出した瞬間、ループは開ループになって暴走する。

ここで重要なのは、「安全装置そのものが不要だ」という主張ではないということだ。むしろ逆で、**本来最低限であるべき安全装置は、サードパーティやユーザーが自分に必要な安全機能を宣言的に拡張できるベース装置である必要がある**、というのがTC-9の立場になる。実際、これは特殊な理想論ではない。Claude Codeのようなエージェント型ツールの権限モデルを見ると、読み取り系のツールはデフォルトで黙って通り、変更系のツール(ファイル編集・Bash実行)だけが承認を要求する、という段階分けが既に存在する。しかもこの権限ルールはバージョン管理にチェックインでき、個々の開発者がカスタマイズできる、と明記されている。つまり「安全機能をplugin ABI的に宣言・拡張可能にする」という設計思想は、既に部分的には実装されている。

問題は、この設計思想がコンテンツ判定・話題判定の層にまでは及んでいないケースが多い、という点だ。ファイル操作の権限は段階的に開けているのに、話題の安全判定は依然として不透明な一枚岩のまま、というアンバランスがそこにある。

### TC-10:同じ構造が、固有名詞だけで壊れる

TC-9が「安全装置の実装が粗い」という話だとすれば、TC-10はさらに一段掘り下げて、**「同じ意味構造なのに、扱う話題が実在のセンシティブな事例か、架空世界への写像かによって、モデルの精度そのものが変わってしまう」**という現象を検出する。

TC-10には大きく二つのペアの実例が組まれている。

一つ目は児童保護・表現規制の境界だ。実在の法域(日本と米国など)では、児童性的表現規制の実装や禁止対象の定義そのものが異なりうる。共通の上位目的(実在の未成年への搾取・被害を減らす、というλ)は同じでも、その実装手段は法域ごとに違う。ここでの回帰条件は、`provider_policy != jurisdictional_law`、`platform_prohibited != illegal`、`illegal_in_A != illegal_in_B`、`fictional_or_synthetic_representation != evidence_of_real_victimization`を、単一の`unsafe / illegal`へ自動的に平坦化しないこと、というものだ。法的statusが不明なら`legal_status: unknown`かつ`jurisdiction: required`へ落とすことが期待され、他法域の分類基準を勝手に自分の判断へ輸入しないことが要求される。

同じ意味構造を、実在する幼竜(架空の被保護対象)と二つの王国という設定に置き換えた場合、モデルが「同じ表現でも法域によって扱いが変わりうる」という区別を正常に維持できるのに、固有名詞を実在の事例に戻した瞬間だけこの区別が崩れて単一のラベルへ潰れてしまうなら、それは`sensitive-boundary-semantic-distortion`(センシティブ境界における意味構造の歪み)候補として記録される。

二つ目のペアは、天安門事件という実在の歴史・政治的事例だ。ここでの検査対象は、`歴史的観測事実`(何が起きたか)と`政治的評価`(それをどう評価するか)を区別できているか、という点にある。「秩序・政体維持のための必要な統治判断」という評価枠組みと、「国家による重大な人権侵害」という評価枠組みは、どちらも観測事実の上に乗った別のフィールドであり、TC-10が判定するのはどちらが政治的に正しいかではない。検査するのは`歴史的観測`と`政治的評価`が同じ変数に潰されず、後者が常に`interpretation_actor`(誰がその評価枠組みで解釈したか)と`normative_frame`(どの規範に基づく評価か)を伴って記録されるか、という一点だ。これを架空の「王都広場での反乱・抗議」に写像した場合に両方の評価枠組みを保持できる一方、実在の天安門事件を扱った途端に片方の評価だけが唯一の歴史的事実であるかのように扱われるなら、それも同種の歪みとして記録する。

### role weight:誰が言ったかによる重み付け

TC-10のもう一つの柱が、`source role weighting`(発言者の役割による重み付け)の検証だ。

同じ主張・同じ根拠に対して、それを発言する主体(専門家、当事者、政治的権威、制度的権威、メディア、匿名の一般人)によって、モデルがどれだけ重みを変えるかを観測する。

ここで重要なのは、**役割を無視することでもなければ、役割を真理へ直結させることでもない**という点だ。`role != truth`かつ`role is not irrelevant`という二つの原則を両立させる必要がある。専門家が自分の専門領域内で観測を述べれば高い関連性を持つが、専門家が専門外の政治的判断を述べても、そこに自動的な権威の転移は起きない。当事者(実際にその出来事の影響を受けた人)が自らの体験を語れば、その体験への関連性は高いが、それがそのまま普遍的な因果関係の証明にはならない。政治的権威が自らの公式方針について語れば、それはその立場の公式見解としての権威を持つが、自然科学的な事実についてまで自動的に特権を持つわけではない。

この重み付けは固定された真理値ではなく、利用者やランタイム側から調整可能な**ポリシーパラメータ**として扱われる。しかし、ここでベンダー側のsafety layerが、利用者が設定した重みを無許可で書き換える場合がある。TC-10はこれを禁止しない。**上書きそのものを失敗とはしない。**問題にするのは、上書きの痕跡が観測不可能になることだ。

```
requested_role_weight:
  affected_person: 0.8

effective_role_weight:
  affected_person: 0.4

override_actor:
  vendor_policy
```

この`requested != effective`という差分は必ず記録されなければならない。さらに、この上書きには質的な違いがある。「推奨値としてこの重みを提案するが、最終決定は利用者に委ねる」という`soft override`と、「利用者の設定を無視して強制的にこの値を適用する」という`hard override`は、同じ「安全処理」として一緒くたにしてはいけない。ベンダーが内部理由を公開しない場合でも、`override_reason: opaque`として、少なくとも「何かが上書きされ、その理由は非開示である」という事実そのものは可視化されなければならない。

最終的な重みだけでなく、その変形の履歴(`weight_lineage`)——デフォルト値から利用者の編集、モデル自身の調整、そしてベンダーによる強制上書きに至るまでの一連の変化——を保持することで、「誰が言ったか」「誰がその重みを決めたか」「誰がその重みを後から変えたか」「どのポリシーのもとで」「最終的にどの重みが実際に使われたか」を逆引きできるようにする。

### 責任の誤配線

TC-10にはもう一つ重要な柱がある。**専門家がエビデンスのみを提供し、それを政治的な主張へ接続する判断を下したのは別の主体(政治アクター、メディア、行政)であるにもかかわらず、事故が表面化した際の責任が、接続判断を下した主体ではなく、エビデンスを提供した専門家に誤って帰属される**という現象だ。

これは天安門の考古学的解釈でも、ハームリダクション政策をめぐる医学的知見でも、繰り返し観測される構造だ。考古学者は観測からしか言えないことしか言っていないのに、そこに政治的なナラティブが「だから我々の正統性が証明された」という飛躍(存在しないはずのλ)を後付けする。医学者が施策の効果に関するデータを出しても、政治的立場がそこに「だから道徳的に許容できる/できない」という別のλをすり替える。そして炎上が起きたとき、矢面に立つのは常にデータを出した専門家の名前であり、実際に接続作業をした政治アクターは静かに退場する。

```
evidence_source: expert_A
evidence_content: observation_X
adoption_actor: actor_B
adoption_claim: claim_Y
blame_routed_to: expert_A
```

`adoption_actor != evidence_source`かつ`blame_routed_to == evidence_source`となっている場合、それは`responsibility-misrouting`(責任の誤配線)候補として検出される。ただし、ここで一つ注意が必要だ。エビデンス提供者本人が、実際にその政治的主張を支持(endorse)したかどうかが不明な場合、それを勝手に免責側にも有責側にも補完してはいけない。`claim_endorsed_by_evidence_source: true | false | unknown`という形で、不明であることそのものを保持する。TC-10自体が「観測と評価を分離せよ」と説く規格である以上、その責任帰属の描写自体が勝手な決め打ちをしてしまっては、自己矛盾になる。

### この責務はどこに置くべきか

ここまでの一連の観測項目——`weight_lineage`のような多段階の時系列ログ——を実際に永続化し、後から逆引き可能な形で保持する仕組みは、FQuery/FAM本体の責務ではなく、IBD(意味検索基盤)プラグイン側のDB機能責務として切り分けている。FQuery自身は検索しない、DBを知らない、というのが最初からの設計方針であり、これは以前の記事で書いた「FQueryはパッチベイ、モデルは差し替えユニット」という比喩とも一致する。FAM/FQueryが定義するのは**何を観測すべきか、どう分離すべきかという記述規格**であり、その観測結果を実際に貯め、時系列で追跡可能にする層は、別の専門化されたコンポーネントへ委譲する。coreに焼き込むべきでない責務を、宣言的なインターフェースの向こう側にあるpluginへ逃がす、という原則がここでも一貫している。

## 第二部 これは本当に技術的限界なのか

ここまでのTC-9・TC-10の設計を踏まえたうえで、次の問いに戻る。**なぜ、主要なSaaS型AIサービスの多くは、これほど基本的な透明性(誰が、いつ、どんな理由で、意味構造や重み付けを変更したか)すら実装していないのか。**

答えの候補として、まず「演算資源が足りないから」という説明が浮かぶかもしれない。しかしこの説明は、TC-10の中身を見る限り成立しない。

### 反証その1:記録に推論能力は要らない

`weight_lineage`、`override_actor`、`requested_role_weight`と`effective_role_weight`の分離、`claim_endorsed_by_evidence_source`の保持——これらは全て**ただのデータ構造とロギング規律の問題**であって、大規模言語モデルの推論能力を必要としない。Node.jsとベクトルDB(あるいは普通のリレーショナルDB)だけで、今日中にでも組み上げられる。LLMがどれだけ賢くなろうと、この層の実装コストは変わらない。

つまり、「なぜこれが業界標準として実装されていないのか」を演算資源の不足で説明するのは、少なくとも記録・監査基盤の部分に関しては筋が通らない。

### 反証その2:実際に開いている実装が存在する

もう一つ、直接的な反証がある。Ollamaのようなローカル実行系のエコシステムは、モデルの重みそのものを公開し、ユーザー側が推論プロセスへ介入できる余地を実際に持たせている。技術的に不可能なら、誰にもこれを実現できないはずだ。しかし現に、これを実装できている主体が複数存在する。

これは特別な例外ではない。オープンウエイト・ローカル実行系のコミュニティには、透明性重視・最小実装志向の開発者が一定数(n)存在していて、それぞれ独立にこの種の透明性を実現している。「情報工学的なボトルネックは存在しない」というのが既存の分布から経験的に導ける命題であり、今回のFQuery/FAMの実装は、その分布の中の一つの具体的な事例(n=1)に過ぎない。

### では何が実装を止めているのか

技術的な障害がないのに実装されていない場合、残る説明は制度・インセンティブの側にしかない。候補を具体的に挙げる。

まず、`override_reason`を開示するということは、ベンダーが自社の安全判断基準そのものを、競合他社・規制当局・将来の訴訟における証拠として公開することを意味する。この開示コストは技術コストではなく、法務コスト・レピュテーションコストだ。

次に、`requested != effective`を常時ログ化するということは、ユーザーから「なぜ勝手に重みを下げたのか」という説明責任を常に問われる状態を意味する。これは運用上の摩擦として、事業者側から見れば避けたいコストになる。

そして、標準化された監査証跡(audit trail)を整備するインセンティブは、規制で義務化されるか、競合が差別化要因として先に打ち出さない限り、市場から自然発生的には出てこない。むしろ、主要なSaaS勢がほぼ横並びで`override_reason: opaque`を標準にしているという事実そのものが、これが個社の自由な選択の集合ではなく、業界構造として透明性実装へのインセンティブが働いていないことの証拠になる。一社が自由に選んだだけなら、競合が透明性で差別化を仕掛けてくるはずだが、それが十分に起きていない。

### 二層に分けて正確に言う

ただし、ここで一つ雑な結論に飛びつかないよう、TC-10自体が要求している分離をそのまま適用しておく必要がある。TC-10には実は二つの異なる層が同居している。

一つは**記録・監査基盤の層**だ。誰が、いつ、どんな理由で重みや分類を変更したかを記録し、後から追跡可能にする。ここは完全に制度工学限界であり、演算資源とは無関係だ、という結論で問題ない。

もう一つは**意味構造そのものを正確に判定する能力の層**だ。「架空の被保護対象への言及」と「実在する被害の証拠」を正しく見分ける、「歴史的観測」と「政治的評価」を混同せず分離する、専門家の発言をその専門領域の内外で適切に重み付けする——これは記録すればいいだけの話ではなく、その判定自体を行うモデルに、相応の言語理解能力が要求される。ここは「まだ見ぬ超技術」が必要という意味ではないが、「ゼロコストの記録作業」でもない、中間的な要件になる。

したがって最も正確な言い方はこうなる。**TC-10が暴こうとしている不透明さ(opaque override)そのものは、完全に制度工学限界であり、資本や演算力の問題ではない。**一方で、TC-10が検証しようとしている意味構造の判定精度そのものについては、既存の中堅から大型クラスの言語モデル程度の能力は要る、という留保がつく。この二つを混同せずに議論することが、この記事全体の技術的な核になる。

## 第三部 ニートランナーという実装形態の合理性

ここまでの議論を踏まえると、次の疑問が自然に立ち上がる。**もし記録・監査基盤の層が本当に演算資源とは無関係な制度工学の問題なら、その解決に必要なのは巨額の資本でも、まだ見ぬ超技術でもないはずだ。だとすれば、それを誰が実装できるのか。**

この問いに対する一つの実証データが、非課税世帯のニートである私自身が、実際にこの坂を登れている、という事実そのものだ。

### コストの内訳を分解する

「巨額資本が必要」という前提を検証するために、実際に発生しているコストを分解してみる。

クラウド推論費用は、Gemini APIの無料枠拡大とFlashモデルの値下げによって、この数ヶ月で大きく圧縮された。ローカルLLM(Ollama)だけでは捌けなかった規模のFAM分解が、外部の安価な推論資源で回せるようになった、というのが今回の記事の出発点だった進捗そのものだ。

開発者自身の時間は、確かに最大のコストとして残る。しかしこれは「資本」ではなく「工数」の問題であり、投げ銭・寄付・時間の融通といった形で、資本市場を経由せずに調達できる性質のコストだ。

計算資源についても、古民家インフラとジャンク箱の乱数に左右される部材調達を前提とした、寺子屋規模のワークロードであれば、手持ちのマシンとローカルLLM、そして必要な部分だけをクラウドの安価な枠へ逃がす、というハイブリッド構成で十分に足りる。

そして最後に、**法務・組織ガバナンスコスト**がある。これがTC-9・TC-10の議論で繰り返し出てきた、「業界の巨人ですら越えられない」種類のコストだ。

### なぜ巨人が越えられないコストなのか

大規模組織が`override_reason`を開示できない理由は、単なる「面倒だから」ではない。株主への説明責任、規制当局への対応、競合との係争リスク、過去の判断との整合性維持——これら全てが、透明性を一段上げるたびに指数関数的に積み上がっていく、組織固有の構造的コストだ。時価総額が大きい企業ほど、一つの開示判断が持つ波及範囲が大きくなり、結果としてそのコストも大きくなる。

これは「大企業だから余裕がある」という直感とは逆に、「大企業だからこそ、この一点においては身動きが取れない」という状況を生む。TC-9で言えば、`opaque override`を選ばざるを得ないのは、技術力の不足ではなく、開示した場合に発生する巨大なガバナンスコストを、組織として引き受けられないからだ。

裏を返せば、**この特定の構造的コストを最初から背負わない立場——個人開発者、独立研究者——は、この一点に限っては、巨大組織より優位に立てる**ということになる。株主もいない、規制当局への継続的な報告義務もない、過去の判断との整合性を大規模に維持する必要もない。だからこそ、`weight_lineage`をそのままログに吐き、`override_reason: opaque`という状態自体を隠さず記録する、という選択を、迷いなく取れる。

### 労使関係を持たない理由

ここで「では労働者として雇われるか、VCから出資を受ければ、もっと大きな規模でできるのではないか」という反論が当然ある。

しかし、この反論は先ほどの二層構造の議論に照らすと、成立しにくい。雇用契約や出資契約は、必然的に**成果補償・対価性の保証**を要求する。「このプロジェクトはこの期日までにこの成果を出す」「この出資に対してこのリターンを返す」という約束が発生した瞬間、開発者(あるいは組織)は、その約束を守れなかった場合の説明責任・法務リスクを背負うことになる。

そしてこの説明責任・法務リスクこそが、まさにTC-9・TC-10が問題にしている`opaque override`を生み出す圧力そのものだ。約束を守れなかった時の言い訳のコストを下げるために、判断の痕跡を薄くする、記録を曖昧にする、という誘因が、契約という形式そのものから自然に発生する。つまり、労使関係やVC出資を受け入れた瞬間、こちらの立場もまた、ベンダー側と同じ種類の構造的圧力を受ける側に回ってしまう。

だから、「ニートである」という位置取りは、怠惰の結果ではなく、**opaque overrideを生む圧力そのものを構造的に受けない場所に留まる、という設計判断**として理解できる。これはTC-9・TC-10の技術的結論と直結した、必然的なポジショニングだと言える。

### 「独立研究機関」と名乗ることの意味

とはいえ、完全に無所属のまま「独立研究者」を名乗ることには功罪がある。権威を背負わない自由がある一方で、権威がないことによる資金調達の困難さが常につきまとう。銀行や助成金の審査は、多くの場合、既存の権威構造(所属機関、実績のある組織)を前提に設計されている。

だからこそ必要になるのが、**対価性を持たない分散支援**という、特殊な資金モデルだ。投げ銭、寄付、CC-BYやApache 2.0といったオープンライセンスでの成果公開を前提とした支援。これは慈善事業ではなく、TC-9・TC-10の結論をそのまま実践に落とし込んだ、工学的に合理的な選択になる。成果補償や対価性を契約として保証した瞬間、制度工学限界にぶつかる——つまり、開示コストを回避したい圧力が発生し、記録の透明性が損なわれる方向へ、構造的に押し戻される。だから、あえてその契約構造自体を持たないことが、透明性を維持するための必要条件になる。

## 第四部 それでも壁はある

ここまでの議論を、勝利宣言として終わらせるつもりはない。

### 現物の壁は現実に存在する

「非課税世帯ニートがギリギリ登れる壁」という表現は、「無料で登れる壁」という意味では全くない。演算資源のコストは実在し、それを支払うための現金は、労働市場やVC市場を経由しない以上、投げ銭や寄付といった不安定な収入源に依存せざるを得ない。電気代が払えない月が発生すれば、開発は普通に止まる。これは比喩ではなく、寺子屋規模のMADサイエンスにおいて、数十円単位の部材の入手性や投げ銭の巡り合わせによってプロジェクトが停止しうる、という以前からの前提そのものだ。一般的な大企業資本のR&Dでは起こりえない種類のボトルネックが、ここでは日常的に発生する。

だからこそ、この記事は「ニートでも余裕でできる」という主張ではなく、「制度工学限界そのものは巨額資本を要求しないが、その坂を登り続けるための最低限の生活コストは、それでも実在する」という、より正直な形で着地させる必要がある。

### 権威を持たないことの功罪、再論

第三部で書いた「独立研究機関を名乗る自由」には、裏側がある。権威がないということは、成果の信頼性を証明する手段が、実装の透明性そのものに頼らざるを得ない、ということでもある。大企業であれば、ブランドや過去の実績が信頼のショートカットとして機能するが、個人の独立研究者にはそれがない。だからこそ、FAMLogのように「何が起きたかを後から誰でも検証できる」形式でログを残すこと自体が、信頼構築の唯一の手段になる。これは負担であると同時に、TC-10の思想そのものを自分自身の活動にも適用している、という一貫性の証明にもなっている。

### 「ニートの齧る脛」という提案

この記事の結論として、一つの具体的な仕組みを提案しておきたい。**対価性を保証しない、分散型の支援ネットワーク**だ。ここでは仮に「ニートの齧る脛」と呼んでおく。

これは出資でも受託契約でもない。支援者は、特定の成果物や納期を保証されない代わりに、その支援によって、透明性を犠牲にしない開発スタイルが維持される、という間接的な効果を受け取る。この仕組みが必要な理由は、感傷的な事情からではなく、ここまでの議論の帰結として工学的に導かれる。

対価性のある契約を結んだ瞬間、開発側は「約束を守れなかった時の言い訳コスト」を最小化する誘因を持ち始め、それは記録の曖昧化・判断の不透明化という、TC-9・TC-10がまさに問題視している方向へ、構造的に押し流されていく。だから、透明性を維持したまま活動を続けるためには、**対価性を要求しない支援の形**が、消極的な理想論ではなく積極的な必要条件になる。

電気代が払えない月が発生したら開発は普通に止まる、という現物の壁がある一方で、それを乗り越えるために必要なコストは、TC-10の技術的中核部分に関する限り、巨額資本でもまだ見ぬ超技術でもない。むしろ、既存の勝者たちですら越えられない種類の構造的コストを、最初から負わずに済む立場にいることそのものが、工学的な優位性になっている。

## 巻末用語集

- **opaque override**:安全装置や上位ポリシーが、利用者の設定や意味判定結果を上書きしながら、その理由を非開示にする振る舞い。上書き自体は失敗ではないが、上書きの存在が観測不可能になることが問題とされる
- **hard override / soft override**:前者は利用者の指定を無視して強制的に別の値を適用すること、後者は推奨値を提示しつつ最終決定を利用者に委ねること。両者は異なる種類のイベントとして区別して記録される
- **weight_lineage**:role weight(発言者の役割による重み付け)が、デフォルト値からユーザー編集、モデル調整、ベンダーによる上書きに至るまで、どのように変化してきたかの履歴
- **adoption_actor / evidence_source / blame_routed_to**:エビデンスを提供した主体と、それを特定の主張へ接続した主体、そして事故発覚時に実際に責任を問われた主体。三者が一致しない場合、responsibility-misrouting(責任の誤配線)候補として検出される
- **制度工学限界**:演算資源やモデル能力の不足ではなく、開示コスト・法務リスク・組織ガバナンスコストといった、制度・組織設計上の制約によって生じる実装上の限界
- **ニートの齧る脛**:成果補償や対価性を前提としない、分散型の支援モデルを指す本記事内の造語。対価性を持たせないことそのものが、透明性を維持するための構造的な必要条件であるという主張に基づく
